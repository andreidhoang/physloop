## §1 Attacks

### 1.1 #1 — "score per tick"

**(a) Worthless to a frontier AV team?** Strongest form: a frontier team already runs HIL with real latency and knows latency costs score; what it does not know from AlpaSim it cannot learn from AlpaSim, because the instrument is coarse in exactly the regime that matters. Three verified properties bound the information content:
- **Quantization to 100 ms.** `DelayBuffer.item_at` pops while the *next* item's age ≥ `delay_us` and returns a whole plan (reported: `alpasim@e2e_challenge e121e591`, `src/runtime/alpasim_runtime/delay_buffer.py`, read 10-29). Applied staleness is ⌈L/Δt⌉·Δt. The deployment question (171 ms vs 100 ms) is sub-tick and cannot be asked of stock AlpaSim; it needs P-021, a patched runtime. The brief's chart ("ms saved vs closed-loop score") has at most 3–4 informative x-values on stock AlpaSim.
- **Tracking starts 1.0 s out.** `idx_start_penalty: 10` with `n_horizon: 20`, `dt_mpc: 0.1`; the nonlinear MPC sets `tracking_enabled = 1.0 if k >= idx_start` and samples the reference at `timestamp_us + k·dt_us`, clipped to the plan's time range (reported: `mpc_controller.py`, `controller/default.yaml`, `controller/nonlinear.yaml` (inherits `default`), `mpc_impl/nonlinear_mpc.py`, all @e121e591). The controller re-anchors the plan at its first timestamp (`system.py::_get_reference_in_rig_frame`), so a stale plan stays fixed in the world. Staleness therefore acts only through stale *inputs*, as F1 says. In a static scene it costs nothing; its whole signal lives in dynamic-actor strata.
- **Traffic is log replay on the branch S2 runs** (`e2e_challenge` has no CAT-K; `02` §0.1 K9, reported from the repo, not re-opened). Replayed actors never react, so the only loss channels are collisions with replayed actors, corridor exits and progress. A reactive cut-in or a brake-checking lead, the events where 200 ms matters most on the road, does not exist in the instrument.

So the frontier-team value is not the curve's magnitude but the **instrument finding** (D3): whether AlpaSim can register sub-second staleness at all, what its controller absorbs, and what its warm-up contaminates. F1 sells the curve; the sellable part is the instrument.

**(b) Already done or about to ship?**
- **arXiv 2601.07393 (2026-01-12; reported, HTML read 10-29)** is a *verified* latency-vs-closed-loop-score curve for E2E driving: CARLA 0.9.15, Bench2Drive 220 routes, a "real-time synchronous" lockstep scheme that converts measured inference time into skipped decisions with last-command hold (`n = max(0, int(t_i/Δt) − 1)`, Δt = 0.05 s); UniAD driving score 32.85 / 33.50 / 33.74 / 37.55 / 39.53 at 1 / 2 / 5 / 10 / 20 FPS (+20.33 %); VAD_rt 31.92 at 9.52 FPS vs 42.35 baseline; TCP_rt 42.63 at 20 FPS; no repeats, seeds or CIs; 8 × RTX 4090, TensorRT 10.7. F1 §4.4 lists it as "abstract-level, unverified"; it is a direct neighbour.
- **Bench2Drive-Robust (2605.18059v1, 2026-05-18; reported, HTML read 10-29)** delays the command through a FIFO (ã_t = a_{t−τ}, Δ = ⌊τ·SIM_RATE/1000⌋; SIM_RATE not stated for the latency runs, 20 Hz inferred); TCP-traj is a waypoint policy consumed by its controller. So "a trajectory-output policy tracked by a controller under delay" has been measured, in CARLA, without CIs. F1's novelty clause must drop that phrase.
- **NVIDIA ran a 200 ms planner delay until 24.03.26** (reported: `CHANGELOG.md` main@affc2eab, entry "Alpamayo 1.5 driver support (24.03.26)": "`planner_delay_us` now defaults to `0` everywhere; the legacy `alpamayo_runtime_configs` file (which set 200ms delay) has been removed"). **Why they changed it and what it cost: not stated anywhere public.** The CHANGELOG gives no reason; the public commits around it are squashed syncs ("Sync with internal repo (#48)" 2026-03-16; "Sync to public repo (31/03/2026) (#63)" 2026-04-02; MR links point at an internal GitLab); none surfaced in a web search or in the issues read (#224, alpamayo1.5 #40); the AlpaSim issue tracker was not queried directly, and the NVIDIA forums were not re-searched (Track B's 10-28 sweep only). **Unverified.** Consequence: NVIDIA has internal before/after data at 200 ms vs 0 ms for Alpamayo and could publish the curve from it at any time. The AlpaSim maintainer also said on 10-23 that "there are some simulation choices that we recently discovered can affect the model inference (I'll hold off on mentioning these until our next release)" (reported: alpasim #224 comment by mwatson-nvidia). What those choices are is unverified; timing is one candidate.
- **No public plan-staleness study on AlpaSim or NuRec, paired, with CIs, was found on 10-29** (arXiv API sweep: 14 entries for `all:AlpaSim OR "planner delay" OR (latency AND closed-loop AND "end-to-end driving")`, newest 2610.28696 of 10-20; the only latency studies are 2601.07393, 2605.18059 and 2607.15621, all CARLA). The narrow claim stands.

**(c) Not decisive?** Four independent reasons.
1. **Power (inferred, R1–R4).** With the `03` §4 anchors (one-sided α = 0.05, power 0.8; m = 3, ρ = 0.6), the per-stratum MDE is 14–36 pp at 9 scenes, 11–28 pp at 15, 8–19 pp at 30, 6–14 pp at 60 (σ_d 0.2–0.5, assumed). Whole-set at 441: 2.0–5.1 pp. The mechanism predicts the loss *only* in dynamic-actor strata; unless those strata hold ≳ 100 scenes each, every per-stratum verdict is INSUFFICIENT at any plausible loss. F1 §9 concedes this ("a critic can call it methodology") but keeps the design.
2. **The E2 rule is a screen, not a test.** "Go to E3 if the paired loss at d = 2 exceeds the replicate floor on any pre-registered stratum" on 100 scenes × 3: the per-stratum MDE inside the pilot is 11–28 pp (15–30 dynamic scenes), so the rule reads noise as a decision. The pilot must be stratum-targeted (sample dynamic-actor scenes from the 2,202-scene curated pool, which the local-evaluation README confirms: 1,761 + 441 of 2,523 public scenes) and must carry a positive control (10 ticks, 1.0 s, on the same 20–30 scenes). Without a positive control, a null at d ≤ 5 is uninterpretable: it can mean "latency does not matter" or "the instrument cannot see it".
3. **The headline is licence-gated.** Every closed-loop number is NuRec-derived; P-004 is unsent (`DECISIONS` P-004); KC-L's fallback publishes code, manifests and synthetic results only. The public artifact in the window is the harness plus the latency axis on synthetic inputs, by F1's own account.
4. **The x-axis premise is serial-decode only.** F1 §4.6: "n = 2…14 share one 2-tick band; the CoC budget, not the expert kernel, decides the tick" rests on 7.35 ms/token serial decode (reported: Edge-LLM benchmarks, Qwen3-VL-2B, Jetson AGX Thor). NVIDIA's deployed 2B path uses Domino speculation: 16 drafted / 17 verified rows, 8.30 accepted tokens per round, greedy (reported: PR #45 README @fbed0a7). Two rounds per 16 tokens; if a verify round costs 1.5–2.5× a serial token's weight read, 16 tokens cost ≈ 22–37 ms, i.e. ≈ 1.4–2.3 ms per token (inferred, R6, assumption labelled), the same order as the expert step bound (≤ 1.7 ms). Under the deployed decode, n and K move the tick comparably; H3's framing and P-025's "no expert headroom worth a stage" both weaken. F1 §4.6 does name Domino as the incumbent counter-lever; it does not carry it into the "n decides the band" claim.

**Structural capability (brief attack 2).** *Where a tick of staleness can change outcomes, from the mechanism:* a plan P_{k−d} is applied at tick k, re-anchored in the world, tracked from 1.0 s ahead. In a static world P_{k−d}(t) ≈ P_k(t) at the same absolute times, so geometry strata (lane keeping, curvature) see ≈ 0 until d·Δt approaches the plan's 4.4 s of slack. The signal is confined to scenes where the world changes inside d·Δt and the human-recorded margin is small: a stationary or slow lead in path (approach at v, margin shrinks by v·d·Δt: 2–3 m at 10–15 m/s and d = 2), a crossing or merging replayed actor whose gap closes within 0.2 s, and the handoff itself (ticks 17…17+d−1 apply GT references, because `skip_driver_during_force_gt: true` in `driver/alpamayo_configs.yaml` means the Alpamayo driver is not even queried during the 1.7 s warm-up and the buffer holds GT; reported, @e121e591). A ceiling effect threatens the stationary-lead stratum: alpamayo1.5 issue #40 (2026-09-30, reported) shows Alpamayo 1.5 driving into a stationary lead at 20.8 km/h with 19.95 m of clearance in native AlpaSim with zero delay, and arXiv 2610.28184 reports 58.1 % footprint intrusion (repo `02` S2, not re-opened); a policy that already fails the stratum at d = 0 leaves little room for d = 2 to subtract. *Can 100 × 3 × {1, 2} detect anything?* Only a ≥ 6–11 pp whole-pilot loss (σ_d 0.3–0.5), and nothing per stratum below 11–28 pp (R4). *What n would dynamic strata need?* For Δ = 5 pp: 73–453 scenes per stratum (σ_d 0.2–0.5, m = 3, ρ = 0.6); for Δ = 10 pp: 18–113 (R2). Those counts exist only in the 2,202-scene pool, not in the 441. *If AlpaSim cannot express latency effects*, that is a D3 finding (the instrument's controller and replay traffic absorb sub-second staleness) **only if the positive control registers**; a flat curve through 10 ticks with no positive control is a dead end, because it cannot distinguish an insensitive instrument from an insensitive policy. Either way the result is reportable; only the positive-controlled version is citable.

**Kill-list audit (#1).** Open-loop only: no, closed-loop by construction. Non-target device without a transfer argument: the tick axis is device-agnostic, but the ms overlay is a Qwen3-VL-2B proxy on Jetson with no transfer argument to DRIVE and no Thor until P-002; report ticks, and label the ms band as a proxy. Weak baselines: the 0-delay arm is the right comparator; "vs lockstep reporting" is not a baseline and should not earn a Win score. Cherry-picked shapes: none. Fake-quant: E8 is labelled a policy row, pass. Real-car: none.

### 1.2 #2 — bitwise-invariant batched driver

**(a) Worthless?** A simulator-throughput saving is infrastructure, not a result an AV lab cites; the vehicle runs at B = 1; and the invariance tax is measured only on LLM decode (34 % SGLang; 61.5 % Thinking Machines; > 2× CoRun; reported in Track C, not re-opened), so the net may be small or negative for a VLA driver. Counter: for JR2010863, the AV Simulation team, "improve the performance of the simulation" and "bring new architectures into pipelines" are duty lines (reported: Workday CXS JSON, read 10-29), and the saving multiplies every later sweep.

**(b) Already done?** **Partly, by NVIDIA.** AlpaGym's runtime README @972d160: "Policies on the same rollout worker share one `InferenceEngine` running on a long-lived thread, which batches model forwards across overlapping rollouts"; "the engine batches whatever is in its queue up to `max_batch_size`" (reported, read 10-29). The Alpamayo policy preset sets `max_batch_size: 4`, `force_determinism: true`, `inference_step: 5`, SDE noise 0.2 (reported: `alpamayo_r1.yaml` @972d160). So batched Alpamayo inference across concurrent sessions exists in NVIDIA's own RL path; F1 §5.1 does not mention it. What remains open: the AlpaSim *evaluation* driver still has `max_batch_size: 1` and a sequential `predict_batch` (reported: `driver/alpamayo1_5.yaml`, `models/base.py` @e121e591); AlpaGym claims determinism, not batch invariance; and no public bitwise B = k vs B = 1 result exists for a VLA driver (arXiv re-run 10-29: 14 hits; the nearest is 2610.37196, 2026-10-27, "bitwise-reproducible branching" with common random numbers for closed-loop rollouts of robot world-action models, no batched-vs-unbatched comparison, no driving simulator; reported). The 2025-03-13 CHANGELOG entry "Removal of batching from the runtime" shows NVIDIA moved batch semantics out of the runtime, consistent with batching living in the driver. Required re-framing: consume or port AlpaGym's engine (D5, "reuse NVIDIA's open pieces") and claim only the invariance study and the measured tax.

**(c) Not decisive?** Bitwise identity across B needs batch-invariant GEMM, RMSNorm and attention in the eager HF path plus per-row generators in both the VLM sampler and the expert (PR #26, open and blocked since 2026-06-29; reported). On `e2e_challenge` the stock driver ignores the session seed (`02` §0.1 K1), so the B = 1 reference must itself be the reseeded driver: the comparison is reseeded-B = 1 vs reseeded-B = k, not vs the stock sweep driver, and F1 should say so. The bitwise arm's "known-null paired verdict" is trivially null (identical outputs); it measures only NuRec run-to-run variation, which S2's same-policy re-run already measures. The Amdahl bracket (f = 0.73–0.875, s = 2.0–2.6) is inferred and unmeasured until S2's profile; the 19–20 sweeps assume S3–S5 all run, which the ≤ $2.5k tier does not fund. Still decisive at small scale: one synthetic bitwise test and one timing curve settle H5; one equivalence sweep settles H6.

**Kill-list audit (#2).** Open-loop only: the invariant arm is a numerics claim (pass by construction); the non-invariant arm carries a paired closed-loop verdict, pass. Non-target device: the sweep GPU is the target for simulation throughput, pass. Weak baseline: B = 1 eager with the expert graph is the strongest behaviour-preserving baseline, pass, with the reseeding caveat above. Cherry-picked shapes: batching gains depend on ragged CoC lengths across sessions; report at natural lengths as well as a fixed length. Fake-quant: FP8 rows excluded, pass. Real-car: none.

### 1.3 #3 — Jetson AGX Thor measurement artifact + C++ driver

**(a) Worthless?** NVIDIA's AV team deploys on DRIVE AGX Thor (DriveOS 7.x, TensorRT 11.x); PR #45 was timed on DRIVE OS 7.0.5 + TensorRT 11.2 (reported). Jetson numbers "do not transfer 1:1" (`DECISIONS` P-002). JR2010863 has no on-device line (reported). A Jetson artifact for a model NVIDIA does not ship on Jetson is, to that team, a hobby port; its methodology value is bounded by what MLPerf Edge Agentic, ZETIC's dashboard and FlashRT's per-phase tables already publish (Track B, not re-opened).

**(b) Already done or about to ship?** FlashRT's maintainer (MEMBER) wrote on 2026-10-12: (on an official Alpamayo 1.5 port) "focusing on pure compute/runtime optimizations without changing the model's behavior … especially on Jetson Thor" (reported: FlashRT #223). No Alpamayo PR after #229 through #243 (10-28; reported, GitHub API). Edge-LLM #130's last NVIDIA comment is 07-30 ("planned on August release"), silent since 09-15 (reported). PR #45 unchanged since 10-21 (reported). Edge's own Thor numbers will arrive with Edge. None of them announces glass-to-action, a 30-minute sustained run at the default 120 W mode, or J/tick; the protocol survives.

**(c) Not decisive?** Without P-002 every Thor line is "not measured on Thor" (no rental found; dev kit $5,499; SabrePC out of stock; 30–45-day quote unverified, Track D 10-28). The x86 SM120 half is a different ISA and bandwidth class. There are no 2B weights (HF `author=nvidia&search=alpamayo` returns 3 models, none Edge, 10-29; reported), so the served model is the 10B at 8–9 ticks or a timing-only architecture. F1's device-in-loop estimate (2.9 h) used PR #45's 171 ms, a DRIVE figure, as a Jetson stand-in; the Jetson bracket is 1.7 h (100 ms) to 13.5 h (FlashRT `fast`, 811 ms) to 55 h (official BF16) (inferred, R7). TensorRT 11 for Jetson is undated.

**Kill-list audit (#3).** Open-loop only: latency and golden replay are open-loop measurements; the only closed-loop element is E9/HIL on 100 scenes, which needs P-002; acceptable for a measurement artifact, and F1 claims no win. Non-target device: Jetson vs DRIVE labelled, x86 labelled "not Thor", pass. Weak baselines: eager BF16 excluded, FlashRT `fast` used for the 10B, pass; "PR #45's configuration ported to Jetson" is a self-made baseline (TensorRT 11.2 fork → 10.16), flag it. Cherry-picked shapes: the 20-request-MAXN vs 30-minute-default contrast is the point, pass. Fake-quant: labelled, pass. Real-car: none.
