- **VERIFIED:** the claim matches the primary source, possibly with a precision note.
- **PARTLY:** the core is right, but a part, date, attribution or wording is wrong. Corrected wording is given.
- **CONTRADICTED:** the primary source says otherwise.

## Corrections, ordered by how much they matter for a plan document

1. **V16: Model naming.** "AM 1.5 Nano / AM 1 Nano" are **not** unreleased models. NVIDIA's own GitHub repos describe the released 10B checkpoints as "Alpamayo 1.5 Nano" and "Alpamayo 1 Nano"; Alpamayo 2 Super is 34B. PR #45 only says its Thor code should also work, unmeasured, on those standard 10B models. Fix every plan or ledger line that treats "Nano" as a new or 2B model, including L5 1.12 ("neither name is on HF" is true only because HF uses the `-10B` suffix).
2. **V2g: AlpaGym is not frozen.** `main` has been quiet since 2026-07-21, but public NVIDIA branches carry commits to 2026-09-03:
   - a cosmos-rl 0.4.4 bump;
   - cluster rollout-transport hardening;
   - humanoid and VLA integration.

   Together with the README's "early but active development", any "AlpaGym frozen at 972d160" statement and the race check for an AlpaGym scaling study need rewording. Pins may move at the next sync.
3. **V2c: AlpaGym's shipped default config does not train.** With `n_generation: 1` and `kl_beta: 0`, every advantage is 0 and the trainer skips the optimizer step. An S4 config must set `n_generation ≥ 2`; NVIDIA's presets use 2–6.
4. **V4: AlpaSim's driver does not pin Alpamayo.** `alpamayo1_5` is installed from git with no rev, and neither branch commits a `uv.lock` (#207 is still unanswered). So:
   - the Alpamayo package in any AlpaSim driver image depends on the build date;
   - the manifest must record the installed alpamayo1.5 commit;
   - PR #36's CUDA-graph API is present only in builds after 2026-08-29, and AlpaSim never enables it.

   PR #36's latency numbers are preliminary, from AlpaGym workloads with one paired sample per model. The 160/160 bitwise result comes from a PR comment.
5. **V10 and V13: Harmonizer and topology protocol.**
   - The `e2e` competition preset (`ec2.yaml`) renders unharmonized.
   - The `e2e` dev default passes `--enable-harmonizer`.
   - `main` passes no flag.
   - NVIDIA *plans* to enable the harmonizer for the final reruns (#222).

   `8gpu_32rollouts` is the EC2 production topology per NVIDIA's own `e2e_challenge` README; in #222 the reporter says it, not NVIDIA.
6. **V24–V26: Seeding.**
   - On `e2e_challenge`, the request seed reaches the driver and is dropped, and there is no determinism switch.
   - On `main`, per-tick reseeding exists but is off in every shipped Alpamayo config.
   - CAT-K (on `main` only) samples unseeded.
   - The NuRec run-to-run variation statement is a hedged recollection ("I believe … might"), not a measurement.
7. **V32: Challenge replicas.** It is 16 driver replicas (4 per GPU on GPUs 4–7, 2 rollouts each, ≤ 16 GiB each), not "4 replicas". `8gpu_alpamayo1_5_eval` exists on `main` only.
8. **V14: PR #44 is open and not marked draft.** The 1.77 s/step figure is a 16-node (128-GPU) 2B stage-1 reference run.
9. **V15: PR #42's on-policy schedule.** 75k of 100k is the reproduced experiment config; the generic `baseline.yaml` uses 60k of 80k.
10. **V20: NeMo-RL version.** GDPO arrived in v0.6.0 (2026-04-30); v0.7.0 (2026-07-29, not 07-25) added PPO.
11. **V6: TensorRT plugin timing.** IPluginV2DynamicExt has been deprecated since TensorRT 10.0 and is still declared in 11.x. Holoscan 5.0.0: PyPI 2026-10-20 UTC, GitHub release 2026-10-21 UTC. ModelOpt 0.48.0rc1 is dated 2026-10-19, not 10-17.
12. **V3: Jerk primitive.** No jerk or comfort scorer exists, but `utils_rs` already has `Trajectory.jerk()`, which lowers the cost of the gated jerk-scorer row.
13. **V27: Reference results.** Only three of the eight reference results are ≈ 3 MB; five are ≈ 1.0–1.4 MB.
14. **Attribution and wording.**
    - V18: ECO and 2610.28184 are NVIDIA-*co-authored* and led elsewhere.
    - V23: "internal" is an inference; AD-Memo also uses an 8B Alpamayo 2 checkpoint.
    - V11: #72 says "no short-term fix; run NRE in its own pod", not "unsupported".
    - V30: 75 % and 58 % are derived numbers.
15. **V22: Price basis.** State the method (per-offer median of `dph_total/num_gpus`). Note that RunPod and Nebius 8×H100 figures are per-GPU list prices × 8, that RunPod's "Secure" tier label could not be verified from the static page, and that vast's $19.20 8×H100 offer exists but is unusable.
16. **V1: Sourcing note.** The split counts come from the public card; the parquet was not inspected.
