# Vast guest host check — engineering acceptance contract

Written before implementation or any remote execution, 2026-11-01. Agent-authored engineering requirements, not Huy's scientific prediction or an AlpaSim experiment.

**Placement:** S2/G1 and G7 environment admission, supporting `02_PHYSLOOP_PLAN.md` S2 run-method/topology registration and mandatory performance/monitoring instrumentation (lines 281, 303–319). The user authorized a temporary Vast VM setup/check followed by cleanup; the coordinating agent owns the actual order, cost ceiling, external watchdog and destruction. This script grants no new spending authority.

**Mechanism:** the adopted AlpaSim Compose deployment requires a working Docker daemon, NVIDIA GPU device reservations, bridge-network service discovery, shared bind mounts and the guest host PID namespace. VM administrator access makes these plausible but does not establish GPU counter support. A synthetic CUDA test can reject broken GPU execution without accessing a model or gated dataset.

**Engineering expectations, fixed before the check:**

1. The guest reports Linux x86_64, OS/init identity, current privilege and noninteractive sudo availability, exact GPU identity and driver, and Docker Engine/Compose/buildx versions. Missing required commands fail the relevant check; absent optional tooling is UNVERIFIED, not PASS.
2. Public CUDA 12.8.1 compilation and execution produce 1,048,576 exact unsigned-integer outputs matching the CPU reference, with zero mismatches across three repeated GPU launches. Unsigned modulo arithmetic is intentional; this is not floating-point model validation or a latency benchmark.
3. An actual buildx build succeeds, and two Compose services exchange an exact synthetic message using Compose DNS and a private bridge network. The client reads a file written through their shared bind mount, verifies that its PID namespace equals the guest Docker host's, and repeats the CUDA known-answer test with GPU reservation enabled.
4. Installed Nsight/DCGM tools and available permission information are recorded. Installed host `ncu` profiles one actual synthetic CUDA kernel with its basic metric set, and installed host `nsys` traces CUDA. The compiled program uses NVCC's static CUDA-runtime default and runs on the guest for these probes; any loader/tool incompatibility remains a failed diagnostic. NVML-backed `nvidia-smi` reports power, temperature, clocks and performance status. DCGM discovery, profiling-field enumeration and three tensor-active samples are attempted when `dcgmi` exists. A missing daemon/tool, permission denial, unsupported field or N/A sample leaves monitoring **UNVERIFIED**; this script never converts an unsuccessful probe to zero. Tool absence does not establish unsupported hardware. A successful command alone does not establish useful telemetry or complete S2 readiness. The operator must review actual values.
5. The script records per-check exit statuses and preserves logs/source files. Cleanup removes only its uniquely named containers, Compose network, build image and temporary workspace; it does not prune unrelated Docker resources. Public image cache may remain until the coordinator destroys the VM and attached storage.
6. Added before first remote execution: on GPU 0, query CUDA total/free memory and allocate the smaller of 72 GiB and 75% of the currently free bytes, rounded down to an 8-byte boundary. If less than 8 GiB is free, fail rather than attempt the allocation. Fill every allocated 64-bit word with its index XOR a fixed constant, verify every word in a second GPU pass, and compare 1,024 evenly spaced CPU-copied samples including both endpoints against the CPU reference. Zero mismatches are required. Report total/free/allocated bytes and release the allocation. The CUDA process has a 30-second inner timeout and its Docker command a 60-second outer timeout; on failure, immediately remove only its named container. This establishes integrity only for the reported allocation and samples, not every advertised VRAM byte, sustained reliability, or a latency measurement.
7. Optional tensor-active positive control, specified before its execution: `scripts/vast_tensor_control.cu` uses cuBLAS `cublasGemmEx` with 2,048 × 2,048 all-one FP16 matrices, FP32 accumulation/output, alpha=1, beta=0 and tensor-operation math requested. Each of the 4,194,304 output values must be exactly 2,048 after warm-up and after the control window; changing one CPU-copied value to 2,049 must produce exactly one detected mismatch. After two warm-up GEMMs, repeat batches of 64 GEMMs with synchronization until a CUDA-event control window reaches approximately five seconds; a 12-second host guard bounds the loop between batches and the coordinator applies a 30-second process timeout. Record GEMM count solely as evidence that work was submitted, not as a speed/throughput measurement. Start DCGM sampling before the workload and retain idle/busy/tail samples. If a supported tensor-active field is available, at least one valid sample during the control window should be greater than zero; this is an engineering responsiveness expectation, not a scientific tolerance. A missing/N/A field or unavailable daemon remains UNVERIFIED. Persistent zero with a correct GEMM is an inconclusive monitoring control that requires checking sampler alignment and actual tensor-kernel selection, not evidence that the GPU lacks tensor cores. No model, renderer, licensed data or scientific inference is involved.

8. Optional exporter check, specified before execution: use the public NVIDIA exporter 4.8.4 / bundled DCGM 4.6.1 image at amd64 digest `sha256:804c17f67ab63e8a4dd5301546beefaa104129f833dae4a68f5ff7c4819f471b` in embedded mode. Stop the task-installed DCGM 4.7.1 service first; do not attach an older exporter client library to that newer host engine. Bind only `127.0.0.1:9400`, use the image's default counters, preserve startup logs, and collect fourteen timestamped scrapes spanning the same known-answer GEMM control. HTTP success and workload success are necessary, but the actual finite metric values must be reviewed; expect a positive tensor-active sample during the load and retain missing fields. No Prometheus, Kubernetes, public port or alerting deployment is claimed. Remove the uniquely named exporter/load containers afterward. The coordinator applies a five-minute outer timeout in addition to the script's per-command limits.

9. Optional non-invasive XID subscription diagnostic, specified before execution: `scripts/vast_nvml_xid_probe.cpp` uses the official NVML header and actual installed driver library on GPU 0. Query the supported-event mask; if its XID bit is advertised, create an event set, register only `nvmlEventTypeXidCriticalError`, wait at most 100 ms, free the set and shut down NVML. Print every API return code and named status/driver description. Successful registration followed by `NVML_ERROR_TIMEOUT` means subscription available with no event received in that short wait; event delivery and the DCGM/exporter XID path remain unverified, never a zero-error or hardware-health result. An absent bit, unsupported/failed registration, or unexpected wait error remains explicit. If a natural XID arrives, preserve its code and return a distinct operator-review status; never inject an error. Compile against the public CUDA image's NVML stub only at link time, execute against the real driver library, and apply a ten-second outer timeout. CPU fake-NVML tests cover these outcomes before the remote check. [Official NVML event API](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlEvents.html).

10. After all needed guest evidence has been copied and its hashes verified, test the existing stop-only watchdog against this same task VM with a new short deadline. It must bind the exact ID/unique label, request control-plane stop after that deadline, and use fresh inventory to establish stopped/absent state; CLI prose alone is not completion. The original sixty-minute monitor remains armed throughout. This is an early cleanup test, not another rental. Preserve the real provider state transition, then destroy the exact task instance/storage and verify absence. An unknown terminal-state spelling is retained as a real integration finding and must not be interpreted as proof of continued compute or proof of completed cleanup without independent inspection.

**Bounds and decision:** each command has a timeout; an additional 20-minute in-guest watchdog terminates the main host probe and runs cleanup. Image pull is capped at 10 minutes. FAIL on any required execution/deployment check means host deployment is not admitted. Successful deployment is only `DEPLOYMENT_PASS_MONITORING_REVIEW_REQUIRED`, never permission to run scientific S2 or a claim that all requested monitoring fields exist. Root's independent provider-side watchdog remains necessary: a guest timeout or guest shutdown does not stop billing.

**Inputs:** public `nvidia/cuda:12.8.1-devel-ubuntu22.04`, public NVIDIA profiling/monitoring packages and the explicitly pinned exporter above, plus synthetic source. Record resolved image IDs/RepoDigests and installed package versions. Official [CUDA tags](https://hub.docker.com/r/nvidia/cuda/tags?name=12.8.1-devel-ubuntu22.04) expose the CUDA tag (amd64 compressed size about 4.79 GB, a public snapshot rather than a transfer forecast). [NVIDIA source](https://gitlab.com/nvidia/container-images/cuda) documents Container Toolkit use. Standard public-software terms apply, including the CUDA container's displayed NVIDIA Deep Learning Container License; do not claim the software has no license. No PAI-AV, NuRec, model weights, provider account keys or gated-asset acceptance actions.

**Reproduction, after the coordinator admits the temporary rental:** `bash scripts/vast_s2_host_probe.sh /absolute/new/evidence-directory`. The output directory must not already exist. The script neither installs packages nor changes services, GPU driver configuration, privileges or provider resources. Missing setup is recorded for the coordinator's decision.
